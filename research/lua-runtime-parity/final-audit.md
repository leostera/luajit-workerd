# LuaJIT host-capability parity audit

**Status: incomplete.** This audit extends the prior matrix audit at `98760d713` with the shared `RequestScope` implementation (`7c7a49353`), opt-in inbound request-body streaming (`cbb9da4b2`), backpressured outbound pass-through and synchronous Lua upload producers, structured URL parsing, bounded random bytes, UUID generation, bounded EVP digests, and optional request CF metadata on `leostera/luajit`. The source-of-truth checklist remains [feature-matrix.md](feature-matrix.md); this report summarizes verified coverage and does not upgrade partial or blocked rows into parity claims.

## Coverage review

The registered JSG inventory in `src/workerd/api/rtti.c++` contains 45 groups. A fresh source-to-matrix check found 45 matching rows, with no missing, extra, or duplicate families. Family dispositions are 6 supported Lua surfaces (some partial), 18 not applicable to the Lua host-capability scope, and 21 blocked on explicit services, lifecycle, or security contracts. The matrix separately covers worker configuration/bindings, service linking, `WorkerInterface` lifecycle, operational behavior, security posture, and runtime limits, using `workerd.capnp`, `Server::makeWorker()`, and the I/O interfaces as sources.

Verified Lua capabilities are deliberately narrow:

- The experimental HTTP worker keeps the `{ fetch = function(request) ... end }` module contract. Inbound bodies remain buffered by default; `luaRequestBodyStreaming = true` opts into request-local chunk reads (64 KiB per read, 1 MiB total) without changing the default `request.body` string. String-valued `workerd.fetch()` request bodies and handler response bodies remain buffered to 1 MiB; streamed inbound bodies can be passed through with backpressure, and Lua producer functions can supply synchronous binary-safe chunks up to 64 KiB each, with a 1 MiB upload limit. `workerd.sleep()` and host operations yield through per-request Lua coroutines.
- `workerd.fetch()` uses only the linked `globalOutbound` route. Outbound response bodies are request-scoped streams read in bounded chunks with `workerd.readBody()`; `readAll()` and explicit/automatic cancellation are covered. Requests interleave at host yield points. Lua `LuaIoContext` and JavaScript `IoContext::IncomingRequest` both compose the runtime-neutral `RequestScope`, which applies per-invocation subrequest admission and observer wrapping. Lua tests verify rejection before route dispatch and successful observer wrapping. The standalone server injects an unrestricted policy and the base no-op observer, matching standalone workerd's current policy/observer behavior; this does not establish Cloudflare production provider wiring or production quotas/metrics.
- `workerd.parseUrl(url[, base])` is a small Lua-native structured parser backed by workerd's KJ URL parser; it supports absolute remote URLs and relative resolution, returns plain component/query tables, and reports invalid input as `nil, error`. It is not a mutable WHATWG URL class.
- `workerd.randomBytes(size)` and `workerd.randomUUID()` delegate to the request's injected KJ entropy source, shared with workerd's standard request context. Byte output is capped at 64 KiB; UUIDs use workerd's version-4 generator. `workerd.digest()` supports case-insensitive MD5, SHA-1, and SHA-256/384/512 names, binary-safe input/output, and a 1 MiB input cap, using workerd's EVP digest implementation. MD5 and SHA-1 are legacy choices, not suitable where collision resistance is required. Signature, encryption, streaming-digest, and key-management operations remain unsupported.
- Optional incoming `cfBlobJson` is decoded lazily on first `request.cf` access and cached as a fresh per-request Lua table; malformed JSON is a catchable Lua error only when accessed. This preserves metadata availability for configured listeners without claiming JavaScript `CfProperty` defaults, freeze behavior, or Access bindings.
- Text, binary-data, and JSON configuration bindings are installed before module evaluation under `workerd.bindings`. JSON `null` uses `workerd.null`; values share the mutable service-lifetime Lua state.
- Runtime failures retain Lua source location and message; the server logs uncaught handler errors and returns a generic 500. Outbound fetch propagates internal and user trace parents through a `lua.fetch` child span.
- Configured unsupported bindings, Durable Object storage, scheduled/alarm interface calls, WebSocket upgrades, and CONNECT are rejected or fail explicitly as documented.

Lua remains experimental and trusted-code-only. Standard Lua libraries include OS and native facilities; there is no Lua CPU/memory quota, sandbox, or V8 inspector. The audit makes no claim that Lua is safe for untrusted tenant code.

## Material gaps

1. **Streaming body generation:** `workerd.fetch()` can pass through `request.bodyStream` and pull synchronous Lua producer functions with backpressure, but producer functions cannot yield for asynchronous I/O. Handler response bodies must remain strings buffered up to 1 MiB; a streaming return value would change the handler response contract and requires user approval. String uploads remain buffered to the same limit.
2. **Provider-specific policy and metrics:** The shared `RequestScope` invokes an injected subrequest policy before dispatch and wraps clients with the invocation observer; tests prove both hooks. Standalone workerd supplies an unrestricted policy and base no-op observer, consistent with standalone JS behavior. The public source does not establish that Cloudflare production providers inject equivalent policy/metrics for Lua, so production parity must not be claimed without that verification and user acceptance of any exclusion.
3. **Events and actors:** Scheduled handlers need runtime-neutral lifecycle, retry, cancellation, trace/metrics, and `waitUntil` ownership. Alarms and Durable Objects need actor identity, persistent state, per-actor concurrency, eviction, and retry semantics. Those models are absent; adding callbacks over service-global Lua state would not reproduce actor lifecycle behavior.
4. **Other operational APIs:** There is no Lua structured logging or public request metrics/tracing API, and no CPU/memory enforcement. These are documented as gaps rather than inferred from error logging, trace-parent propagation, observer hooks, or coroutine support.
5. **Other cryptographic operations:** Lua exposes bounded secure random bytes and UUID generation plus non-streaming MD5, SHA-1, and SHA-256/384/512 digests over inputs up to 1 MiB. Signature, encryption, key import/usage, streaming-digest, and `CryptoKey` binding behavior remain unsupported.
6. **Storage and service bindings:** Analytics Engine, Cache API, Hyperdrive, process-local memory cache, KV, Queues, R2, and Worker RPC have no Lua binding adapters or typed host channels. These require per-binding configuration, cancellation/accounting, and service-specific lifecycle contracts; the matrix marks them blocked rather than claiming HTTP covers them.
7. **Specialized host and cross-service APIs:** WebSockets and CONNECT lack Lua host handlers; sockets need explicit egress policy to avoid bypassing workerd controls; HTMLRewriter needs a non-JSG callback/stream boundary; webfs needs a managed root and permission model; request clocks need the Spectre-mitigated TimerChannel; Access identity, tail events, worker inheritance, and async upload producers each lack their required request/event/configuration contract. These are material exclusions. The matrix classifies web-platform-only conveniences separately as not applicable.
8. **Other configuration integrations:** Worker Loader, containers, SQL (which depends on actor storage), module fallback/extensions, secret/environment-derived and wrapped bindings, and parameterized bindings remain unavailable. Each needs a Lua-specific config, capability-transfer, or trust contract; the matrix records the concrete dependency rather than treating `globalOutbound` or service-global Lua state as equivalent.

The `http-network` task's contract is met for the selected experimental HTTP surface: outbound response streaming/backpressure, opt-in inbound request streaming, backpressured pass-through and synchronous producer uploads, disconnect cancellation, error handling, configured routing, injected subrequest admission/observer hooks, and interleaving are covered by tests and documented. Yieldable upload producers remain an explicit exclusion, and no Cloudflare production provider wiring is claimed.

## Acceptance required before completion

The matrix currently records 21 blocked families and 18 not-applicable families, alongside partial supported surfaces. Before the overall parity goal can be marked complete, the user must accept the material exclusions documented above, especially the unverified Cloudflare production policy/metrics wiring, service/storage bindings, actor/event lifecycle, specialized network/storage APIs, resource enforcement, and the response-streaming contract boundary. No handler signature, response-body type contract, or trusted-code boundary has been changed. If any listed exclusion should instead be pursued, identify it and work can continue against that scope.
