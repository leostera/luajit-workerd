# workerd LuaJIT host-capability parity matrix

- **Status:** Exhaustive _family-level_ checklist; implementation status is updated incrementally and must not be read as symbol-by-symbol API parity.
- **Architecture note:** [architecture.md](architecture.md) documents the host-operation boundary, request/coroutine ownership model, and implemented shared subrequest scope.
- **Latest audit:** [final-audit.md](final-audit.md) reports verified coverage, evidence, and material remaining gaps.
- **Source snapshot for initial audit:** workerd `8548f49da652625d8d7d1db84cbd868f85e0dc4f` (`leostera/luajit`), audited 2026-10-13. Re-audit the current branch head before completion.
- **Goal:** Track workerd host capabilities available to JS workers and decide which have meaningful Lua equivalents. This is not an ECMAScript/V8 semantic checklist or a symbol-by-symbol inventory of every JSG member.
- **Contract:** Keep the Lua module-returned `{ fetch = function(request) ... end }` shape. Do not add `env`/`ctx` arguments. Lua remains experimental and trusted-code-only; no sandbox claim.

## Status key

- **AS — Supported/implemented:** The stated Lua surface exists and has targeted tests; partial coverage is described in the current-support column.
- **NA — Not applicable:** JavaScript-, V8-, JSG-, or internal-only feature without a useful Lua host capability.
- **BL — Blocked/dependent:** A prerequisite or contract decision must be resolved before implementation.

[L1, L3, L11]                                                                                                                                                                 |

[L1, L2, L8] |

[L1, L2]                                                                                                                          |

## Audit sources

All paths are relative to workerd root at the source snapshot above. Evidence labels used above:

- **L1:** `docs/reference/lua-runtime.md` and the Lua runtime/worker-interface implementation and tests listed below.
- **L2:** Experimental `workerd.fetch()` adds bounded response-body pulls via `workerd.readBody()`/`readAll()`. Runtime/server tests cover mapping, request interleaving, incremental reads, explicit body cancellation, cross-request handle rejection, client disconnect cancellation, configured routing, injected admission rejection before dispatch, observer wrapping, opt-in incremental inbound body reads, async chunk boundaries, binary chunks, partial-read errors, stream limits, config validation and disconnect cancellation. Tests verify chunked pass-through while inbound data is still arriving, Lua-generated binary chunks, per-chunk and total size limits, producer error mapping, and cancellation after client disconnect. Yieldable body sources and Cloudflare production provider wiring remain unverified.
- **L3:** Text, binary-data, JSON, and `fromEnvironment` config bindings populate `workerd.bindings` before module evaluation. Runtime/server tests cover binary and null conversion, mutable service-global values, malformed JSON, set/empty/unset environment values, service-construction capture, duplicate names, and rejection of unsupported binding variants.
- **L11:** HTTP service bindings are exposed as `workerd.bindings.NAME.fetch(request)` and dispatch through their configured worker channel, not `globalOutbound`. The selected channel still passes through the request's `RequestScope` admission and observer hooks. Runtime tests verify the binding-index route and accounting hooks; the server test verifies two configured-worker channels with a distinct global outbound route. Typed Worker RPC and storage/service integrations remain unsupported.
- **L4:** Runtime tests verify scheduled and alarm interface calls fail explicitly; server tests verify Durable Object storage rejection and WebSocket/CONNECT 501 responses.
- **L5:** Runtime tests verify Lua source/message error provenance, outbound internal/user trace-parent propagation under `lua.fetch`, and a later request succeeding after cancellation; server tests verify uncaught-error logging and generic 500 responses. No metrics observer or Lua structured logging API is claimed.
- **L6:** `workerd.parseUrl()` uses `kj::Url` in the Lua runtime adapter and returns plain Lua tables. Runtime tests cover canonical absolute parsing, relative resolution, duplicate and valueless query parameters, percent-decoded path components, userinfo, and invalid URLs/bases.
- **L7:** `workerd.randomBytes(size)` and `workerd.randomUUID()` use the invocation's injected KJ entropy source; byte output is bounded to 64 KiB. Runtime/server tests verify host delegation, byte bounds/empty output, UUID formatting, Lua argument errors, descriptor validation, and server wiring.
- **L8:** `request.cf` decodes optional invocation `cfBlobJson` into a fresh Lua table. Runtime tests verify nested data, per-request isolation, mutation isolation, absence, and catchable errors on lazy parse failure; a server test verifies the configured `cfBlobHeader` route.
- **L9:** `workerd.digest()` uses workerd's OpenSSL-compatible EVP digest implementation for case-insensitive MD5, SHA-1, and SHA-256/384/512 identifiers, with binary-safe input/output and a 1 MiB input limit. Runtime tests verify known vectors, binary input, case-insensitive naming, supported boundary size, and errors for unsupported algorithms, wrong types, and oversized input.
- **L10:** `workerd.hmac()` computes HMAC over binary Lua strings, caps raw keys at 64 KiB and data at 1 MiB, and accepts the same digest algorithm allowlist. `workerd.verifyHmac()` uses `CRYPTO_memcmp()` for equal-length MACs and returns false for mismatches. Runtime tests verify MD5/SHA-1/SHA-2 vectors, binary keys/data, case-insensitive naming, exact limits, verification success/failure, and argument/size/algorithm errors. The raw key is not a protected `CryptoKey`.
- **L12:** Workerd config accepts Lua HMAC CryptoKey bindings only for non-extractable raw/hex/base64 key material, HMAC SHA-1/SHA-2, and `sign`/`verify` usages. Runtime userdata is opaque and only usable with matching HMAC operations; key bytes are cleansed when the server-owned key is destroyed. Runtime/server tests cover usage enforcement, opacity, HMAC signing/verification, all supported key encodings and hash algorithms, string and object hash forms, extraction rejection, malformed key data, missing algorithm hash, and unsupported configuration usages.
