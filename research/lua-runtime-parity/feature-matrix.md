# workerd LuaJIT host-capability parity matrix

- **Status:** Exhaustive _family-level_ checklist; implementation status is updated incrementally and must not be read as symbol-by-symbol API parity.
- **Architecture note:** [architecture.md](architecture.md) documents the host-operation boundary, request/coroutine ownership model, and implemented shared subrequest scope.
- **Latest audit:** [final-audit.md](final-audit.md) reports verified coverage, evidence, and material remaining gaps.
- **Source snapshot for initial audit:** workerd `8548f49da652625d8d7d1db84cbd868f85e0dc4f` (`leostera/luajit`), audited 2026-10-13. Re-audit the current branch head before completion.
- **Goal:** Track workerd host capabilities available to JS workers and decide which have meaningful Lua equivalents. This is not an ECMAScript/V8 semantic checklist or a symbol-by-symbol inventory of every JSG member.
- **Contract:** Keep the Lua module-returned `{ fetch = function(request) ... end }` shape. Do not add `env`/`ctx` arguments. Lua remains experimental and trusted-code-only; no sandbox claim.

## Status key

- **AS — Already supported (partial surface):** Exists in the Lua runtime, but only to the extent stated in the current-support column.
- **EI — Implementable, not implemented:** A Lua-shaped counterpart is plausible; this is a disposition, not a commitment to clone JS names or semantics.
- **NA — Not applicable:** JavaScript-, V8-, JSG-, or internal-only feature without a useful Lua host capability.
- **BL — Blocked/dependent:** A prerequisite or contract decision must be resolved before implementation.

## Current Lua contract (implementation snapshot)

| Area                        | Current behavior and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker source/config        | `Worker.luaScript`; server requires `--experimental`. `luaRequestBodyStreaming` optionally enables inbound body reads and is rejected without `luaScript`. `makeWorker()` accepts text, data, and JSON bindings under `workerd.bindings`; it rejects other binding types, compatibility date/flags, DO config/storage, workflows, tails, module fallback, Access binding config, Cache API outbound config, and container-engine config. `globalOutbound` is linked for experimental `workerd.fetch()` calls. [C1, C2, L3]                                             |
| Module/handler              | Execute one Lua source chunk; it must return a table with callable `fetch`. Text/data/JSON bindings are installed before evaluation. Shared LuaJIT state persists for the configured service lifetime. Standard libraries are opened, including OS/native facilities; trusted code only. [L1, L3]                                                                                                                                                                 |
| Bindings                    | `text`, `data`, and `json` values populate `workerd.bindings` before module evaluation; JSON `null` uses `workerd.null`. The table and nested values are mutable service-global Lua state. [L3]                                                                                                                                                                                                                                                                   |
| Request/response            | Inbound method, URL, headers (array of `{name,value}`), and body become a Lua request table. `request.body` is a string by default; `luaRequestBodyStreaming` opts into `request.bodyStream` plus bounded `workerd.readRequestBody()` calls (up to 64 KiB, 1 MiB total). `workerd.fetch()` accepts strings (1 MiB), the current request stream in streaming mode, or a synchronous producer function returning chunks up to 64 KiB (1 MiB total); handler response bodies remain strings limited to 1 MiB; header count is 128. Handler response needs integer status 200–599 and string body. `workerd.fetch()` returns a request-scoped response-body stream readable with `workerd.readBody()` (1–64 KiB chunks), `workerd.readAll()`, and `workerd.cancelBody()`. [L1, L2] |
| Async/concurrency           | Each fetch runs in a coroutine against the shared state. `workerd.sleep(ms)`, `workerd.fetch(request)`, response-body reads, opt-in request-body reads, and stream cancellation suspend the handler and allow interleaving. No `waitUntil`/background-task API. Lua execution itself is cooperative: synchronous loops do not yield. No CPU/memory quotas. [L1, L2]                                                                                                                          |
| Other WorkerInterface paths | WebSocket upgrade and CONNECT return 501; scheduled events and alarms fail as unsupported; custom events call `notSupported()`; `prewarm()` is a no-op; no worker test handler. [L1, L4]                                                                                                                                                                                                                                                                          |
| Tests                       | `src/workerd/rt/luajit/lua-runtime-test.c++`, `src/workerd/server/server-test.c++`; tests cover the experimental gate, supported simple bindings, duplicate/unsupported binding rejection, custom `globalOutbound` routing, incremental body reads, pass-through and producer uploads, bounded random bytes/UUIDs, structured URL parsing, and cancellation. [L1, L2, L3, L4, L6, L7, C2]                                                                                                                                                                        |

## Audit sources

All paths are relative to workerd root at the source snapshot above. Evidence labels used above:

- **L1:** `docs/reference/lua-runtime.md` and the Lua runtime/worker-interface implementation and tests listed below.
- **L2:** Experimental `workerd.fetch()` adds bounded response-body pulls via `workerd.readBody()`/`readAll()`. Runtime/server tests cover mapping, request interleaving, incremental reads, explicit body cancellation, cross-request handle rejection, client disconnect cancellation, configured routing, injected admission rejection before dispatch, observer wrapping, opt-in incremental inbound body reads, async chunk boundaries, binary chunks, partial-read errors, stream limits, config validation and disconnect cancellation. Tests verify chunked pass-through while inbound data is still arriving, Lua-generated binary chunks, per-chunk and total size limits, producer error mapping, and cancellation after client disconnect. Yieldable body sources and Cloudflare production provider wiring remain unverified.
- **L3:** Text, binary-data, and JSON config bindings populate `workerd.bindings` before module evaluation. Runtime/server tests cover binary and null conversion, mutable service-global values, malformed JSON, duplicate names, and rejection of other binding variants.
- **L4:** Runtime tests verify scheduled and alarm interface calls fail explicitly; server tests verify Durable Object storage rejection and WebSocket/CONNECT 501 responses.
- **L5:** Runtime tests verify Lua source/message error provenance, outbound internal/user trace-parent propagation under `lua.fetch`, and a later request succeeding after cancellation; server tests verify uncaught-error logging and generic 500 responses.
