# workerd LuaJIT host-capability parity matrix

- **Status:** Exhaustive _family-level_ checklist; implementation status is updated incrementally and must not be read as symbol-by-symbol API parity.
- **Architecture proposal:** [architecture.md](architecture.md) documents the host-operation boundary, request/coroutine ownership model, and unresolved accounting seam.
- **Source snapshot for initial audit:** workerd `8548f49da652625d8d7d1db84cbd868f85e0dc4f` (`leostera/luajit`), audited 2026-10-13. Re-audit the current branch head before completion.
- **Goal:** Track workerd host capabilities available to JS workers and decide which have meaningful Lua equivalents. This is not an ECMAScript/V8 semantic checklist or a symbol-by-symbol inventory of every JSG member.
- **Contract:** Keep the Lua module-returned `{ fetch = function(request) ... end }` shape. Do not add `env`/`ctx` arguments. Lua remains experimental and trusted-code-only; no sandbox claim.

## Status key

- **AS — Already supported (partial surface):** Exists in the Lua runtime, but only to the extent stated in the current-support column.
- **EI — Implementable, not implemented:** A Lua-shaped counterpart is plausible; this is a disposition, not a commitment to clone JS names or semantics.
- **NA — Not applicable:** JavaScript-, V8-, JSG-, or internal-only feature without a useful Lua host capability.
- **BL — Blocked/dependent:** A prerequisite or contract decision must be resolved before implementation.

## Current Lua contract (implementation snapshot)

| Area                        | Current behavior and evidence                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker source/config        | `Worker.luaScript`; server requires `--experimental`. `makeWorker()` accepts text, data, and JSON bindings under `workerd.bindings`; it rejects other binding types, compatibility date/flags, DO config/storage, workflows, tails, module fallback, Access binding config, Cache API outbound config, and container-engine config. `globalOutbound` is linked for experimental `workerd.fetch()` calls. [C1, C2, L3]                                             |
| Module/handler              | Execute one Lua source chunk; it must return a table with callable `fetch`. Text/data/JSON bindings are installed before evaluation. Shared LuaJIT state persists for the configured service lifetime. Standard libraries are opened, including OS/native facilities; trusted code only. [L1, L3]                                                                                                                                                                 |
| Bindings                    | `text`, `data`, and `json` values populate `workerd.bindings` before module evaluation; JSON `null` uses `workerd.null`. The table and nested values are mutable service-global Lua state. [L3]                                                                                                                                                                                                                                                                   |
| Request/response            | Inbound method, URL, headers (array of `{name,value}`), and fully buffered body become a Lua request table. Inbound/outbound request bodies and handler response bodies are limited to 1 MiB; header count is 128. Handler response needs integer status 200–599 and string body. `workerd.fetch()` returns a request-scoped response-body stream readable with `workerd.readBody()` (1–64 KiB chunks), `workerd.readAll()`, and `workerd.cancelBody()`. [L1, L2] |
| Async/concurrency           | Each fetch runs in a coroutine against the shared state. `workerd.sleep(ms)`, `workerd.fetch(request)`, response-body reads, and stream cancellation suspend the handler and allow interleaving. No `waitUntil`/background-task API. Lua execution itself is cooperative: synchronous loops do not yield. No CPU/memory quotas. [L1, L2]                                                                                                                          |
| Other WorkerInterface paths | WebSocket upgrade and CONNECT return 501; scheduled events and alarms fail as unsupported; custom events call `notSupported()`; `prewarm()` is a no-op; no worker test handler. [L1, L4]                                                                                                                                                                                                                                                                          |
| Tests                       | `src/workerd/rt/luajit/lua-runtime-test.c++`, `src/workerd/server/server-test.c++`; tests cover the experimental gate, supported simple bindings, duplicate/unsupported binding rejection, custom `globalOutbound` routing, incremental body reads, and cancellation. [L1, L2, L3, L4, C2]                                                                                                                                                                        |

## Runtime-neutral lifecycle and correctness checklist

| Concern                   | Current state                                                                                                                               | Required parity disposition / tests                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Request body              | Inbound and outbound request bodies are fully buffered to 1 MiB before use; outbound response bodies are streamed to Lua in bounded chunks. | Streaming request work belongs to `streams`/HTTP phase; test over-limit, abort during read, binary body and partial read failure.          |
| Response body             | Lua string copied to byte array and written once.                                                                                           | Stream/backpressure model; test slow downstream, write failure and request cancellation.                                                   |
| Header semantics          | Request headers converted to array pairs; response pairs added through KJ HTTP headers.                                                     | Preserve duplicate headers and validation policy; test invalid names/values and duplicates.                                                |
| Lua state ownership       | One VM per configured service; request coroutines use that VM on event-loop thread.                                                         | Keep access serialized; test simultaneous requests around yields, service teardown and no coroutine/reference retained after cancellation. |
| Async bridge              | Descriptor-driven `sleep`, `fetch`, `readBody`, and `cancelBody` operations.                                                                | Ensure exactly-once resume, cancellation, rejection mapping, and no raw KJ/V8 types enter Lua; test host and stream errors.                |
| Errors/observability      | Lua errors become KJ failures; no JS inspector.                                                                                             | Provide source-aware structured logs and request correlation; test compile/startup/runtime/async errors.                                   |
| Compatibility and rollout | Experimental gate only; no Lua compatibility date.                                                                                          | Specify Lua API versioning and tests before stable exposure; do not use unrelated JS flags.                                                |
| Tests/build               | Dedicated runtime and server tests; Bazel target for Lua runtime and server.                                                                | Add focused tests per implemented row and run applicable Bazel targets, formatting and diff checks.                                        |

## Audit sources

All paths are relative to workerd root at the source snapshot above. Evidence labels used above:

- **L1:** `docs/reference/lua-runtime.md` and the Lua runtime/worker-interface implementation and tests listed below.
- **L2:** Experimental `workerd.fetch()` adds bounded response-body pulls via `workerd.readBody()`/`readAll()`. Runtime/server tests cover mapping, request interleaving, incremental reads, explicit body cancellation, cross-request handle rejection, client disconnect cancellation, and configured routing; observer/accounting parity and streaming request bodies remain unverified.
- **L3:** Text, binary-data, and JSON config bindings populate `workerd.bindings` before module evaluation. Runtime/server tests cover binary and null conversion, mutable service-global values, malformed JSON, duplicate names, and rejection of other binding variants.
- **L4:** Runtime tests verify scheduled and alarm interface calls fail explicitly; server tests verify Durable Object storage rejection and WebSocket/CONNECT 501 responses.
- **C1:** `src/workerd/server/workerd.capnp` worker union, binding union, and worker configuration fields.
- **C2:** `src/workerd/server/server.c++` (`Server::makeWorker()`) and Lua-related cases in `src/workerd/server/server-test.c++`.

Implementation inventory sources:

- JSG groups: `src/workerd/api/rtti.c++`; member lists: each `src/workerd/api/*.h` named by the `EW_*_ISOLATE_TYPES` macros; central registration: `src/workerd/server/workerd-api.c++`.
- Binding/global types: `src/workerd/server/workerd-api.h` (`WorkerdApi::Global::value`); full config schema and binding union: `src/workerd/server/workerd.capnp`.
- Lua implementation/limits: `src/workerd/rt/luajit/lua-runtime.{h,c++}`, `src/workerd/rt/luajit/lua-worker-interface.h`, `src/workerd/rt/luajit/lua-runtime-test.c++`.
- Lua config gate: `src/workerd/server/server.c++` (`Server::makeWorker()` and `LuaWorkerService`); integration tests: `src/workerd/server/server-test.c++`.
- Host lifecycle and events: `src/workerd/io/worker-interface.h`, `src/workerd/io/worker.h`, `src/workerd/io/io-context.h`, `src/workerd/io/observer.h`, and `src/workerd/io/limit-enforcer.h`.
- JSG semantics (excluded from Lua API parity): `src/workerd/jsg/README.md` and `src/workerd/jsg/AGENTS.md`.
